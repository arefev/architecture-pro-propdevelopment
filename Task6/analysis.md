# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. Доступ к секретам:
   - Кто: Пользователь "kubernetes-admin" с принадлежностью к группам "kubeadm:cluster-admins" и "system:authenticated"
   - Где: Запрос на получение секрета с именем "bootstrap-token-3tnwjk" в пространстве имен "kube-system"
   - Почему подозрительно: Запрос был отправлен пользователем с правами cluster-admin и обращался к секрету, который не удалось обнаружить (код 404 — NotFound). Такое поведение может указывать на попытку получить доступ к несуществующему секрету или к ресурсу, к которому у пользователя отсутствуют необходимые разрешения.

2. Привилегированные поды:
   - Кто: system:serviceaccount:kube-system:daemon-set-controller
   - Комментарий: В пространстве имен kube-system был создан под с названием "kube-proxy-34wrt". Он запускался с привилегированным контекстом безопасности, что может представлять потенциальный риск для безопасности кластера. Подобные привилегированные поды способны выполнять операции и получать доступ к ресурсам на уровне хоста, что делает их потенциально опасными для общей безопасности инфраструктуры.

3. Использование kubectl exec в чужом поде:
   - Кто: minikube-user
   - Что делал: Пользователь minikube-user развернул под "privileged-pod" в пространстве имен secure-ops, наделив его повышенными привилегиями и добавив аннотацию "kubectl.kubernetes.io/last-applied-configuration", содержащую сведения о привилегированном контейнере. Кроме того, под включает аннотацию "pod-security.kubernetes.io/enforce-policy", указывающую на использование привилегированного режима. Данное событие можно считать подозрительным, поскольку создание привилегированного пода пользователем может представлять потенциальную угрозу для безопасности кластера.

4. Создание RoleBinding с правами cluster-admin:
   - Кто: ServiceAccount с именем monitoring в пространстве имен secure-ops
   - К чему привело: Присвоение ServiceAccount monitoring роли cluster-admin предоставляет ему полный доступ ко всем ресурсам Kubernetes-кластера. Такое расширенное разрешение может создать риск несанкционированного доступа, изменения либо удаления критичных ресурсов, что потенциально угрожает безопасности и стабильности всей системы.

5. Удаление audit-policy.yaml:
   - Кто: admin
   - Возможные последствия: Был удалён файл "audit-policy.yaml", содержащий конфигурацию аудита Kubernetes-кластера. Такое действие может привести к утрате важной информации о происходящих в кластере событиях, осложнить проведение расследований по вопросам безопасности и затруднить отслеживание пользовательской активности.

## Вывод
Проверка Kubernetes Audit Log показала ряд подозрительных действий, которые могут свидетельствовать о потенциальных угрозах для безопасности кластера. Обнаружены случаи использования повышенных привилегий, создания привилегированных подов, попыток доступа к секретам и удаления важных аудиторских файлов — все эти инциденты требуют внимания и оперативного устранения выявленных рисков.

Для повышения безопасности кластера необходимо внедрить дополнительные меры: ограничить доступ к привилегированным ресурсам, применять строгие политики безопасности, регулярно отслеживать действия пользователей и проводить аудит. Важную роль также играет обучение пользователей безопасной работе с Kubernetes и контроль соблюдения установленных правил.
